# Codebase audit, 2026-09-16

Full-repository audit for defects, one week after the 2026-09-09 audit. Six
reviewers read disjoint slices of the code in parallel (Hub API and MCP server,
capture and sync functions, the AI pipeline, the frontend data layer, the
frontend components, the migrations) and reported only what they had traced
through the actual call path. Every finding below was then re-read in the code
before it was repaired. Where a claim was checked against the live project, that
is stated; no production data or schema was changed by this audit.

## What was checked

`npx tsc --noEmit` (clean before and after), `npm run lint` (0 errors; 1,445
`any` warnings, down from 1,455), `npm test` (84 files green before, 85 after),
`node scripts/check-edge-functions.mjs` (193 files, gates present),
`node scripts/check-brand-strings.mjs`, `npm run build`. The reviewers read every edge function, every `_shared` module, every
hook, every `src/lib` file that touches Supabase or the query cache, every page
and component that writes, the 60 most recent migrations in full and all 211
for cross-cutting patterns.

## Findings and repairs

### Account deletion did not delete the account

Three separate defects, together meaning that "delete my account" either failed
outright or left most of the data behind.

1. **The delete cascade tripped an authorization check.** `enqueue_note_ai_job()`
   raised `not authorized` for any session that was neither `service_role` nor
   the note's owner. GoTrue's `auth.admin.deleteUser` runs with no JWT at all,
   so `auth.role()` and `auth.uid()` are both NULL, the `media_analysis` trigger
   raised inside the cascade, and the whole deletion rolled back. Every user
   with a completed media analysis got HTTP 500 "Failed to delete account".
   The same check made any `UPDATE notes` from the SQL editor or a migration
   fail. Live check: the trigger and both checks present, one of twelve accounts
   holds completed media rows and could not be deleted today.
   Fixed in migration `20260916120000`: a session with no JWT is the database
   itself and is trusted; every session that presents a role is checked as
   before.

2. **About 55 user-owned tables had no foreign key to `auth.users`.** Live
   `pg_constraint`: 33 public tables reference `auth.users`; `contacts`,
   `moments`, `claims`, `contact_interactions`, `hub_api_keys`,
   `mcp_api_tokens` and around fifty more do not. `admin-delete-user` said out
   loud that "notes, contacts, … cascade". They did not, and a Hub API key of a
   deleted account stayed `is_active` and kept reading its orphaned contacts.
   Fixed in the same migration: every public table with a uuid `user_id` column
   gets `ON DELETE CASCADE` from `auth.users`, derived from the catalogue so a
   table added later is covered by re-running the block. Each key is added
   `NOT VALID` then validated; an orphan row already present stops the
   migration naming the table rather than being deleted quietly. A `user_id`
   index is created where none exists, so the cascade does not scan.

3. **`world_preferred_survives_delete` vetoed the cascade.** A BEFORE DELETE
   trigger returning NULL skips the row, and Postgres does not re-check a
   referential cascade afterwards. Hand-typed relationships survived their
   contact's deletion pointing at nothing (live: 20 preferred entries, 1
   preferred relationship exposed). Now a row whose parent is gone goes with it,
   and a session with no JWT is never vetoed; a machine tidy-up of a row whose
   parent still exists is still refused.

4. **OAuth-only users could not delete their account at all.** The only proof of
   identity was `signInWithPassword`; a Google or GitHub account has no
   password and always got "Invalid password". Such an account now confirms by
   typing its e-mail address; accounts with a password re-enter it as before.
   `src/pages/Settings.tsx` shows the matching field.

5. **Both deletion paths left every note attachment in storage.** Only the
   `avatars` bucket was cleared; clips, scans and uploads under
   `note-attachments/<user id>/` (up to 20 MB each, service-role uploads with no
   owner) had no cascade and no policy. `_shared/delete-user-storage.ts` now
   walks both buckets for both functions.

### Google Drive import stopped silently and could import twice

- `gdrive-sync` listed the folder with `pageSize=100&orderBy=modifiedTime`
  (ascending) and never followed `nextPageToken`. Once a watched folder held
  more than 100 already-imported scans, every new scan landed past the end of
  the page and was never imported, with `last_error` set to null on every run.
  Now newest first, following the page token until the run has its ten files.
- Nothing stopped two overlapping runs (the two-minute cron, a Drive push ping
  per upload, "Sync now") from importing the same file: `notes` has no unique
  key on the Drive file id and the `gdrive_imports` row was only written after
  download, upload, note insert and OCR. A run now claims the file by inserting
  the `gdrive_imports` row (UNIQUE on user and file) before any bytes move; a
  second run gets `23505` and moves on. A claim older than thirty minutes is
  treated as abandoned and may be taken over.
- The seen-set was an unpaged select, capped at 1,000 rows; past that, older
  Drive files looked new again. Now paged.

### Bidirectional GitHub pull echoed every pulled file back to the repository

`_shared/github-pull.ts` built `syncByNoteId` once and never refreshed it.
Pulling a remote change updated the note (the trigger stamped `updated_at`) and
the sync log, but the push step still saw the stale `synced_at`, judged the note
"changed since sync", and committed it back with Menerio's frontmatter only,
stripping `aliases:`, `cssclasses:` and any other key the user kept in
Obsidian. A new import whose `title:` differed from the file name was pushed to
`<Title>.md` while `<file>.md` stayed untracked, so the next sync imported it as
a second note, every run. The pull and import steps now record the sync as of
the row's own `updated_at` (returned by the write, so no clock of ours can land
before the database's) and update the in-memory map, so the push step leaves
those notes alone.

### Obsidian block-style tags read as one empty tag

`github-pull.ts` and `github-import-vault` each carried their own inline-only
frontmatter parser, the one `_shared/frontmatter.ts` was written to replace.
For `tags:\n  - work\n  - ai`, the format Obsidian's Properties editor writes,
they read `tags` as `""`, so the note got `tags: [""]` and lost its real ones;
the echo above then wrote `tags: [""]` back to the repository. Both files now
use the shared parser, and an empty value is never a tag.

### Text corruption through `String.replace`

`String.prototype.replace` reads `$$`, `$&`, `` $` `` and `$'` in a replacement
string as patterns. Two places passed user text there:

- `src/utils/markdown-converter.ts` restored inline code that way, so `` `echo $$` ``
  rendered as `echo $` and `` `a$'b` `` spliced the rest of the document into
  the code span; the next autosave persisted it. Verified in a unit test that
  now guards it.
- `_shared/note-edit-tools.ts` (`replace_in_note`) did the same to the model's
  replacement text, so a LaTeX `$$E=mc^2$$` was written as `$E=mc^2$`.

Both use a replacer function now.

### Dated facts (claims)

- Adding a historical claim closed the current one before it started: with
  `employer=Y valid_from 2020`, adding `employer=X 2010-2015` stamped
  `valid_to=2010-01-01` on Y, which then vanished from every "current" view.
  `claimsToSupersede` (both twins) now skips a claim that starts after the
  incoming one; an undated claim is still superseded. Tests extended.
- `addClaimWithSupersede` closed the live claims and then inserted; when the
  insert was refused (nothing validated the date columns, so
  `valid_to: "next year"` failed at the database) the old fact stayed closed
  and the new one never existed. Dates are validated up front, and the insert
  now happens before the closes. `src/hooks/useClaims.ts` had the same order
  plus a swallowed lookup error that inserted a second open value; both fixed.
- `get_claims` applied `limit` in SQL before the `mode` filter, so a subject with
  more closed claims than the limit silently lost current ones. The filter is
  in the query now.

### Offline sync manager multiplied its retry timers

`src/sync/SyncManager.tsx`: while `navigator.onLine` was false,
`reportUnreachable` scheduled a retry and every caller scheduled another, so
each failed attempt armed two timers, each of which ran another attempt. The
count doubled per cycle; a device back from an hour in airplane mode fired
thousands of connect calls at once. One scheduler, one timer, cleared before it
is re-armed.

### Note list collapsed to one row on the desktop path

`useUpdateNote.onSuccess` patched every `["notes"]` cache entry with a boolean
filter on `is_trashed`. On the local-first path those entries hold raw SQLite
rows (the PowerSync hook's `select` maps per observer, not in the cache), where
`is_trashed` is 0 or 1, so the filter kept only the row just merged. The live
query re-runs on the write anyway; the patch is skipped there now.

### Captures

- `telegram-capture` echoed the user's text into a `parse_mode: HTML` message
  unescaped and ignored the response. Telegram refuses a stray `<`, so a note
  reading `if a < b` was saved but its confirmation never arrived and the user
  sent it again. Escaped, and a failed send is logged.
- `ingest-thought` (Slack) ran the embedding and the metadata call before
  answering. Slack retries after three seconds, so a slow day meant two to four
  copies of the note, each charged. A retry (`X-Slack-Retry-Num`) is answered at
  once, and a message whose `ts` is already on a note is not captured twice.
- `receive-note` looked the note up with `maybeSingle()`; once two rows existed
  for one `source_id`, that returned an error the code threw away, `existing`
  read as null, and every later push inserted another copy. Oldest-first with
  `limit(1)`, and the error is checked.
- `menerio-mcp` `capture_note` rethrew every non-credit failure of the metadata
  call before the note row existed, so a provider timeout lost the note. It
  falls back to default metadata like the credit case; `process-note`
  re-extracts later.

### Hub API and MCP server

- The MCP server rewrote the shared `add_collection_item` tool description with
  the current user's collection names and capture instructions on every
  request. The registry is one object per isolate, so two users hitting the
  function at once could each be handed the other's collection names in
  `tools/list`. The description is static now (the per-user guidance is in the
  `list_collections` result it points at), which also saves two queries per call.
- `hybridSearchNotes` capped rows at 50 but reported the uncapped total, so
  `has_more` promised pages that returned empty and an agent following it
  looped. The total is what can be paged.
- `hub-api-notes/search` awaited a call to `search-notes-semantic` with the
  service key as a user bearer, got 401, and never read the result; a failed
  fetch there failed the whole search. Deleted.
- `parseInt("all")` is NaN and walks through `Math.min`/`Math.max`;
  `?limit=all`, `?offset=x` and `?days=week` answered 500. `intParam()` in
  `_shared/hub-helpers.ts` clamps or falls back.
- MCP `update_note` stored `folder_path` verbatim while creation and the Hub API
  normalise it; `/Research/` put the note in a nameless folder above the real
  one. Normalised.

### Frontend

- Deleting a person from the detail pane fired the hard delete (contacts,
  memberships, interactions, relationships, no undo) on a single click of the
  trash icon; the people tree already asked first. The pane asks now.
- Review queue Keep / Roll Back / Never Again could be applied twice on a
  double click: the accept paths insert their rows before the status mutation
  starts, so `isPending` was false for the whole async stretch. One action per
  item at a time.
- `AgentInstructionsTab` defined its form component inside the parent's render,
  a new component type on every keystroke: the textarea remounted, the caret
  jumped to the end, undo history vanished. Hoisted.
- Settings writes reported success on failure (`supabase-js` returns `{ error }`
  rather than throwing): GitHub connection save and disconnect, API key list and
  revoke. Errors are checked. The Slack, Telegram and Discord panels have the
  same pattern and are listed under open items.
- The onboarding wizard stored the avatar's full public URL where Settings and
  Admin expect the storage path, so those pages rendered a doubled URL and the
  old file was never removed. The wizard stores the path; `src/lib/avatar-url.ts`
  renders either form. Settings also removed the old avatar before the new
  upload succeeded, and ignored the profile update's error; order and check fixed.
- Ctrl/Cmd+K was bound by both the command palette and the header search, which
  opened both with the palette's focus trap fighting the input. The search box
  only listens for Escape now.
- Restoring a GitHub version wrote the preview HTML into a Markdown note. The
  Markdown body is kept and restored.
- Removing a note's AI footprint invalidated `["wiki_pages"]`,
  `["profile_entries"]`, `["note_connections"]` (underscored), which match no
  query; deleted entries kept rendering for the cache lifetime and survived
  reloads through the persister. The hyphenated prefixes the pages use are
  invalidated, for single removals too.
- An attachment upload whose `note_attachments` insert failed still reported
  success; the note saved `![[name]]` that could never be resolved again after
  the signed URL expired. The upload is undone and the failure reported.

### The AI pipeline

- **Every note that mentions the owner's own name failed analysis, permanently
  (live, confirmed in production).** `recordDisambiguation` in `process-note`
  looked a "self" decision up with `.eq("target_contact_id", null)`. PostgREST
  sends that as `eq.null`, casts the literal against the uuid column and
  answers 22P02. Before the durable queue that error was thrown away; now the
  execution database wrapper turns it into a transient failure, and after
  three attempts the job is `failed`: no review items, no facts, no moments,
  the note stuck in "processing". Live: of the twelve most recent failed
  analysis jobs, nine carried the owner's name in the extracted people; of 45
  completed jobs, none did. 27 analysis jobs sit in that state. `.is()` for
  NULL, and the wrapper now names the database error instead of the generic
  "Analysis database operation failed" that hid this for weeks. **The 27 jobs
  need re-enqueueing after deploy** (an edit to each note, or an admin
  reanalysis); `enqueue_note_ai_job` does not revive a failed job whose
  fingerprint is unchanged.
- `enrich-person-from-lexicon` used six helpers from `relationship-canonical.ts`
  without importing them. Nothing type-checks the Deno functions in CI, so
  every run paid for the model call, threw a ReferenceError, and the
  background handler swallowed it: tokens charged, zero suggestions, the user
  saw "running". Imported.
- The job worker aborted its call to the executor after 110 s and failed the
  job as `uncertain`, revoking the 300 s lease the executor was still running
  under; its later checkpoints were rejected as stale, the paid work was lost,
  and the job stayed `failed` until the note was edited. A 50-chunk note or a
  Lexicon ingest with four groups gets there. The worker's own timeout now
  leaves the lease alone (the claim RPC reclaims an expired one). Test added.
- The relationship judge rejected, with confidence 1, every role outside a
  private 29-entry list: cousin, grandmother, aunt, step- and in-law roles,
  doctor, therapist, co-founder, all of which `relationship-canonical.ts`
  accepts and stores. `profile-lint` then deleted such rows and the bulk keep
  archived them. The judge now accepts what the canonical registry knows.
- Bulk "keep" on relationship suggestions called the judge per row and archived
  every row the judge did not answer `keep`, including every row where the
  judge could not run at all (no credits, provider down): forty quoted
  suggestions kept on an empty balance were all filed as removed with nothing
  created. Only a judged rejection archives now; an unavailable judge leaves
  the row pending.
- `runWikiStage` turned `BALANCE_UNAVAILABLE` and `REPEAT_CALL_BLOCKED`, both
  raised before the provider is reached, into a terminal `uncertain`; one
  unreadable allowance view fenced the stage for good. Transient now.
- `recompute-all-connections` read a failed `match_notes` call as "no matches"
  and, with an empty keep-set, deleted every semantic connection of the note.
  Same for the two stale-connection reads. A failed read skips the note.
- Bare `JSON.parse` on paid model output at eleven sites, where fenced JSON is
  a documented live failure: group AI (500 after billing), connection
  suggestions (silently empty), the relationship judge, fact classification,
  profile suggestions, media description, the weekly review, moment
  extraction, the profile normaliser (three fenced replies locked the
  subject's plan through the attempt lease) and Lexicon group insights (the
  checkpointed reply was replayed three times, failing the job and dropping
  the paid main synthesis). All use `parseModelJson` now.
- The profile audit read `entry_ids` from a rejected group that carries `ids`,
  so every "do not propose this again" note was empty and the same lossy
  group was proposed and paid for on every round.
- The Lexicon restructure sweep logged every page under the first candidate's
  user id, which showed one user the page slugs of everyone else. Logged under
  the page's owner.
- The admin prompt test charged the admin's balance and counted against the
  repeat breaker, which locked the sixth test of a prompt for an hour; the
  router documents `skipDeduct` for exactly this call.
- A span with no paragraph or sentence boundary (a base64 data URI, a minified
  blob) stayed one chunk, exceeded the embedding provider's input limit and
  failed the job. The chunker hard-splits such spans on code-point boundaries,
  and no longer carries a boundary-less "sentence" over as overlap. Tests added.

### Build and scheduling

- `scripts/check-edge-functions.mjs` derives the cron-gated functions from the
  migrations. Four scheduled jobs (cron.job 9, 10, 11, 15: `gdrive-sync`,
  `gdrive-watch-maintenance`, `profile-lint`, `normalize-profile`) were created
  in the dashboard and never as a migration, so nothing derived them, and
  `gdrive-sync` (every two minutes) could have lost its gate with CI green.
  They are listed with the header-against-env-secret pattern they use.
- `gdrive-sync` and `gdrive-watch-maintenance` had no `[functions.*]` entry in
  `config.toml`; a redeploy could flip them to `verify_jwt = true` and every
  scheduled run would be refused at the gateway. Pinned.
- `20260826094000_cron_shared_secret.sql` (and its byte-identical copy
  `20260829145008`) asserted exactly five `call_edge` jobs; a later migration
  added a sixth, so the file could not be replayed on any database that had it,
  and a fresh database has none. The guard is "at least five, unless there are
  no jobs at all".
- `profile_fields` let any account insert a row with `is_system = true`, and the
  structured-category trigger looked such rows up without a user filter, so one
  account could divert every other account's AI entries for that category into
  review. `CHECK (NOT is_system OR user_id IS NULL)`.
- `github-sync-export` bulk sync read notes unpaged and reported success for a
  vault past 1,000 notes with the rest left behind. Paged.

## Open items, found and not repaired here

Listed so they are not lost; none is silent data loss on an ordinary path.

- Signing out clears PowerSync's local queue; edits made offline and never
  uploaded are gone with it (`AuthContext.tsx`, `recovery.ts`). Needs a drain
  into the recovery journal, or a warning while the queue is non-empty.
- Unpaged reads capped at 1,000 with a UI that implies completeness:
  `useNotesRemote` (web path note list, and folder deletion trashes only what
  the list holds), `useOrphanNotes`, `useWorld` (500 events, 2,000 claims).
- Single-click deletes without confirmation: relationships, entities, facts,
  profile entries, agent instructions, groups, moderation words.
- Slack, Telegram and Discord settings panels, and the admin moderation panel,
  toast success without checking `{ error }`.
- Date-only values compared as UTC: action due dates, moment dates,
  `world-claims.ts` vs `claims.ts` "today".
- Hub API PUT handlers answer 404 for every database error, including a type
  error on an unvalidated field.
- `enforceMcpToolLimit` is read-then-write; a concurrent burst passes.
- `add_claim` accepts an entity `subject_id` without an ownership check (stored
  under the caller's user id, so no cross-user read; the effect is a dangling id).
- "Related notes" on a person scans only the 50 newest notes.
- AI pipeline, found and not repaired: `wiki-ingest` checkpoints the user's
  whole Lexicon inside the paid stage (the 1 MB stage-result cap then fails
  every ingest for a large Lexicon); a 40001 on apply is retried with the same
  stale checkpoints; `process-note` runs paid relationship adjudications
  outside the stage protocol, uncapped, re-billed on every retry;
  `profile-reconcile`'s relationship evidence pass is unreachable (two
  `continue`s cover every row); `profile-audit` treats an unparseable reply as
  a clean scope; outbound provider fetches carry no timeout; the same
  1,000-row select cap in `backfill-person-metadata`, `profile-lint`,
  `profile-reconcile`, `normalize-profile`, `generate-profile-suggestions`,
  `backfill-wikilinks`, `backfill-media-analysis`; contact and page text in
  system prompts without the safety wrapper in `wiki-ingest`, `draft-event`,
  `classify-profile-fact`; OCR bills per page with no page cap.
- CI has failed on the lint warning budget (1,453) since 2026-09-10, when a
  commit took the count to 1,455. This audit brings it to 1,445.
